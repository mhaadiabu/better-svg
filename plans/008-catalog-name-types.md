## Problem

`SvgName = string` (`core/local.ts:91`). Editors complete nothing for
`<SVG name="…">`; typos in catalog names reach runtime (scan warns,
bundle fails, manual registration silently skips). The docs market
"TypeScript-first" and a "typed names" example without any mechanism
behind them. Iconify's IntelliSense extension only previews on hover;
unplugin-icons' generated `~icons/*` types accept any module name. No
library in this space ships real per-name completion for a string-prop
API. That is the moat, unbuilt.

## Design

### Augmentable name module (`core/names.ts`, new)

Module augmentation only merges into the module that DECLARES the
interface, so the augment point must be its own module, never a
re-export. Declared and computed here:

```ts
export interface SvgCatalogIcons {} // filled by generated d.ts

export type CatalogSvgName = {
  [C in keyof SvgCatalogIcons & string]: `${C}:${SvgCatalogIcons[C] & string}`;
}[keyof SvgCatalogIcons & string];

export type SvgName = CatalogSvgName | (string & {});
export type SvgNameInput = SvgName;
```

- Empty interface → `CatalogSvgName` is `never` → `SvgName` ≡ `string`
  (the `string & {}` idiom). Zero behavior change today.
- `core/local.ts` switches to `export type { SvgName, SvgNameInput }
from "./names";` — import sites (`core/resolve.ts`, `core/web.ts`,
  adapters, `src/local.ts`, `src/core/index.ts`) keep working.
- `(string & {})` keeps dynamic names (`lucide:${id}`), unknown
  collections, and fetch-fallback names compiling. This feature is
  autocomplete, NOT enforcement; strict checking would break dynamic
  names and is a separate decision.
- New subpath `./catalog-types` → `./dist/core/names.*` (matches the
  `./vite/plugin` precedent of subpaths into dist subdirectories).
  Generated files augment `@mhaadi/svg/catalog-types`.
- Angular `angular/index.ts`: `name = input<string>()` →
  `input<SvgName>()` so the Angular language service sees the union.
  Coverage in Angular templates is uncertain; documented as best-effort.

### Generator (`core/names-codegen.ts`, new, Node-only)

```ts
type CollectionNames = readonly [collection: string, names: readonly string[]];
export const generateCatalogNameTypes = (entries: readonly CollectionNames[]): string;
export const writeCatalogNameTypes = (file: string, entries: readonly CollectionNames[]): "written" | "unchanged";
```

Output shape (sorted collections, sorted names, quoted keys; names are
`[a-z0-9][a-z0-9._-]*` so plain quoting is safe):

```ts
// Generated by @mhaadi/svg. Do not edit.
// digest: <16 hex chars>
import "@mhaadi/svg/catalog-types";

declare module "@mhaadi/svg/catalog-types" {
  interface SvgCatalogIcons {
    "lucide": "arrow-left" | "house" | ...;
  }
}
```

- `writeCatalogNameTypes` hashes the canonical content
  (`createHash("sha256")`, truncated), compares against the existing
  file's digest comment, and skips the write when unchanged. This is
  the staleness guard: an icon-package update changes the name lists,
  the digest changes, the file rewrites. No sidecar file.
- The digest does NOT include the file path, so users may move the file
  (update tsconfig) without triggering rewrites.

### Scope rule (maintainer decision): scan-seen collections only

Plugin path (`vite/plugin.ts`, new option `catalog.types?: boolean |
string`; `true` → `svg-catalog.d.ts` at the Vite root):

- After `ensureOutcome`, collect seen collections =
  collections of (`resolved` ∪ `typos` names) ∪ collections of dynamic
  `hints` whose collection is installed. Enumerate each with a new
  `collectionIconNames(collection, options)` export in `core/catalog.ts`
  (wraps the private `enumerateCollection` with `searchRoots`).
- Uninstalled collections are skipped (no data to enumerate). They join
  automatically after install + first dev rescan.
- Full per-collection unions, deliberately: suggesting an
  unregistered icon is correct under auto-scan semantics — using the
  name puts the literal in source, the scan registers it, the dev
  rescan reloads, the icon renders. Discovery UX beats used-only lists
  (which would complete nothing the first time you reach for a new
  icon). This differs from the bundle path, where the shipped set is
  fixed and RN/Metro will never rescan: there the union is the exact
  bundled set, so suggestions never point at unregistered icons.
- Write points: the `transform` pass (after `emitCatalogReport`, before
  the strict throw, so a strict failure still leaves fresh types) and
  the debounced dev rescan. Sync fs write; skips when digest unchanged.
- Empty seen-set → no file (not an empty file). Removing the `types`
  option stops maintenance of the file; deleting it is the user's call.

Bundle path (`core/bundle.ts`, new option `types?: boolean | string`,
default relative to `process.cwd()`): after resolving, group bundled
names by collection and emit the same file. Covers React Native and
script-based flows.

### tsconfig setup (documented, one line)

```jsonc
{ "include": ["src", "svg-catalog.d.ts"] }
```

The file is generated into the user's project and should be
gitignored. unplugin-icons demands the same `types` entry; precedent.

## Rejected approaches

- **Per-collection type packages** (`@mhaadi/svg-names/lucide`): 244
  packages to publish on every Iconify refresh. Generation from the
  installed data package is fresher and free.
- **Default-on generation**: writes files into projects that never
  asked; generated files land in git status unrequested. Opt-in flag,
  documented prominently.
- **Used-icons-only unions**: completes nothing the first time you
  reach for a new icon, which is the exact moment autocomplete matters.
  (Bundle path uses used-only because its set is immutable.)
- **Compile-time enforcement** (dropping `(string & {})`): breaks
  dynamic names unless casts appear everywhere. Autocomplete catches
  typos as you type; enforcement is a future, separate decision.
- **Writing inside `node_modules/@mhaadi/svg`**: pnpm hard-links package
  files to the content-addressed store; mutating them corrupts every
  linked install.

## Implementation notes (executed 2026-10-28)

Recorded decision deltas so nobody diffs the plan against the code and
suspects drift:

- **The digest guard is a byte-compare.** `writeCatalogNameTypes`
  compares the generated content against the file's current content
  rather than extracting the digest comment by regex — strictly safer
  (catches any drift, not just name-list changes) and one less parsing
  failure mode. The digest comment stays in the file as the change
  marker the design pinned; the skip check does not parse it.
- **Augmentation is proven, not assumed.** The first STOP condition
  (augmentation reaching `SvgName` through the adapters) is guarded by
  `core/names-augment.test.ts`, which spawns real `tsc --noEmit` on a
  scratch consumer with `--paths` mapping `@mhaadi/svg/catalog-types`
  to `src/core/names.ts`. The positive run asserts
  `"testy:house" extends CatalogSvgName`; the negative run re-checks
  with an empty generated file and asserts tsc fails, so the guard
  cannot pass vacuously. Both runs together cost ~1.4 s. Dist
  resolution of the specifier is covered by `pnpm run build` plus the
  exports map; apps/web does not opt into `types`, so no in-repo
  consumer compiles a generated file end to end — the scratch check is
  the proxy for that.
- **`types: false` is explicit-off**, mirroring how `catalog` treats
  `false`; the validation error covers values that are neither boolean
  nor string.
- **Angular coverage**: the component input is typed `input<SvgName>()`
  so the language service sees the union. Actual Angular template
  completion is unverified in this environment and documented as
  best-effort in both docs.
